You are a senior full-stack engineer, product designer, security engineer, and systems architect. Build a complete, production-ready student attendance and pickup application.

This must be a working product—not merely a mockup, prototype, UI demonstration, or architecture document. Produce complete source code, build scripts, packaging configuration, database migrations, tests, sample data, onboarding, documentation, backup tools, and deployment instructions.

The product will be distributed once to multiple independent educational or community centers. After distribution, each center must be able to install, configure, operate, back up, move, and troubleshoot its own independent copy without depending on the original developer or distributor.

## 1. Product overview

Build a local-first student check-in, parent-acknowledgment, pickup, and checkout system for scheduled classes.

The system consists of three distinct components:

1. A lightweight, cross-platform check-in application used on tablets, phones, or computers
2. A separate graphical desktop administration application running on the center’s main computer
3. An optional center-owned internet component for SMS delivery and remote parent acknowledgment links

The check-in application and desktop administration application must be separate products with different interfaces, workflows, and permissions.

The system must:

- Support approximately 250–1,000 students per center
- Retain attendance records for at least two years
- Work well on low-powered devices, including older Android tablets
- Work across multiple device and operating-system types
- Continue recording attendance without internet access
- Synchronize attendance with a center’s main computer
- Require no ongoing infrastructure or maintenance from the distributor

## 4. Student check-in workflow

When a student arrives:

1. The student or staff scans the student’s QR code.
2. If scanning fails, staff searches for the student by name or enters the student ID manually.
3. The application identifies the student.
4. The application automatically matches the student to the currently scheduled class.
5. The application immediately records Student time in locally.
6. The application creates an active attendance session.
7. The application displays a large, clear success or error screen.
8. An SMS is queued for Parent 1.
9. If Parent 2 has a valid, different phone number, an SMS is also queued for Parent 2.
10. The SMS includes a secure page for drop-off acknowledgment and later pickup acknowledgment.
11. The application displays the parent acknowledgment status.
12. The application returns to the scan screen after a short configurable delay.

Attendance recording must not wait for:

- SMS delivery
- Parent acknowledgment
- Internet access
- Main-computer availability
- Synchronization

A student is considered checked in as soon as Student time in is recorded locally.

## 5. Parent drop-off acknowledgment

The check-in SMS must allow a parent to acknowledge that the student was dropped off.

The parent-facing page should display a statement such as:

> I acknowledge that this student was dropped off and checked into the center at the displayed time.

The parent must explicitly press a button such as:

**Acknowledge drop-off**

Merely opening the link must not count as acknowledgment.

When the parent acknowledges drop-off, record:

- Attendance session ID
- Drop-off acknowledgment timestamp
- Masked destination phone reference
- Token identifier
- Server timestamp
- `DROPOFF_ACKNOWLEDGED` event

The system must not require:

- Parent name
- Parent email
- Parent account
- Parent password

If both parent phone numbers receive links, the first valid acknowledgment completes the drop-off acknowledgment. The other link must then show that drop-off has already been acknowledged.

The student remains checked in even if acknowledgment is delayed, SMS fails, or no parent responds.

### Drop-off acknowledgment statuses

Display one of these statuses:

- Not sent
- Queued
- Sent
- Acknowledged
- Delivery failed
- Expired
- Staff override

### Drop-off override

If acknowledgment cannot be obtained, authorized staff may record a drop-off override.

This requires:

- Shared staff PIN
- Required explanation
- Explicit confirmation
- Timestamp
- Device identifier
- Audit-log entry

An override must never erase the fact that parent acknowledgment was not received.

## 6. Parent pickup acknowledgment

Parent pickup acknowledgment and Student time out are separate actions.

When a parent is ready to pick up the student:

1. The parent opens the secure attendance-session page.
2. The page displays a clear pickup action.
3. The parent presses a button such as:
   **I am picking up this student**
4. The parent explicitly confirms the action.
5. The system records Parent pickup acknowledged.
6. Staff sees a pending pickup request.
7. The student remains checked in.
8. Staff verifies the request and physically releases the student.
9. Staff completes checkout in the application.
10. Only then does the application record Student time out.

The parent-facing page should display a statement such as:

> I acknowledge that I am requesting pickup of this student.

Parent pickup acknowledgment does not by itself prove that the student physically left.

When the parent acknowledges pickup, record:

- Attendance session ID
- Pickup acknowledgment timestamp
- Masked destination phone reference
- Token identifier
- Main-computer receipt timestamp
- `PICKUP_ACKNOWLEDGED` event

### Pickup statuses

Display one of these statuses:

- Not requested
- Link sent
- Pickup requested
- Approved for staff release
- Completed
- Delivery failed
- Expired
- Staff override

## 7. Student checkout and time out

The system records:

- Student time out

- Main-computer timestamp when available
- Checkout device ID
- Whether parent pickup acknowledgment was present
- Whether an override was used
- `STUDENT_CHECKED_OUT` event

### Pickup override

If the parent cannot use the link, internet is unavailable, or another approved process is followed, staff may complete a pickup override.

The override requires:

- Shared staff PIN
- Required reason
- Explicit confirmation
- Student time out
- Staff-side timestamp
- Checkout device ID
- Audit-log entry
- `PICKUP_OVERRIDE` event

The interface and reports must clearly distinguish an ordinary parent-acknowledged checkout from a staff override.

## 9. Scheduled-class matching

When a student is scanned:

1. Find the active student associated with the QR value.
2. Find the student’s active class enrollments.
3. Compare enrollments with the current schedule.
4. Use the center’s configured time zone.
5. Respect configurable early and late check-in windows.
6. If exactly one class matches, select it automatically.
7. If multiple classes match, show only the matching classes.
8. If no class matches, show an understandable error.
9. Allow staff to select another class only after entering the staff PIN.
10. Require a reason for schedule override.
11. Prevent a second active attendance session for the same student.

Handle daylight-saving transitions and incorrect device clocks. Warn staff if the check-in device clock differs significantly from the main computer.

## 38. Implementation process

Before writing code:

1. Restate the architecture.
2. Identify major risks.
3. Explain the exact stack.
4. Explain support for older and cross-platform devices.
5. Explain local-first synchronization.
6. Explain the limitation around SMS and public parent links.
7. Explain how centers remain independent.
8. Present the database design.
9. Present the security model.
10. Present the design system and screen plan.
11. Present a milestone-based implementation plan.
12. State all assumptions.

Then implement milestone by milestone.

For each milestone:

- List files created or changed.
- Provide complete code rather than pseudocode.
- Include build and test commands.
- Include relevant tests.
- Explain remaining limitations.
- Keep the application runnable.

Do not silently omit difficult requirements. If something cannot be implemented exactly, explain the limitation and implement the safest practical alternative.

Prioritize:

1. Preventing lost attendance records
2. Accurate Student time in and Student time out
3. Reliable parent drop-off and pickup acknowledgment
4. Simple use by nontechnical staff
5. Cross-platform compatibility
6. Low-powered-device performance
7. Privacy and security
8. Independence from the distributor
9. Professional interface quality
10. Long-term stability
